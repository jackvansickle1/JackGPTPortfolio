Make the fallback a contract.

Testing an AI-assisted FastAPI endpoint without a network.

By Jack VanSickle · September 26, 2026 · 9-minute read

The failure contract

  1. Invalid input remains a client error.
  2. Unusable model output returns grounded data.
  3. Transport failure marks AI as degraded.
  4. Budget exhaustion returns and caches the fallback.

An API that calls an AI model has at least two products hiding inside it. One is the model-enhanced response you hope to return. The other is the response your users receive when the model is slow, unreachable, or confidently emits the wrong shape.

The second product deserves tests too.

I will use the public JackGPT Market Desk repository at commit 92c022c as a concrete example. Its /api/analyze endpoint assembles a market snapshot, builds a deterministic research brief, and can optionally ask a local Ollama-compatible model to improve the wording. The important architectural choice is that the deterministic brief exists before the model call. AI enrichment can fail without erasing the underlying result.

The goal here is not to test Ollama. It is to prove the FastAPI application's contract at four boundaries:

  1. Invalid client input remains a client error.
  2. Syntactically unusable model output falls back without pretending the whole API failed.
  3. A transport timeout returns the fallback and marks the AI dependency degraded.
  4. Exhausting the endpoint's response budget also returns—and caches—the fallback.

Read the failure policy before writing the test

FastAPI's official Handling Errors guide makes the intended mechanism explicit: raise HTTPException; do not return it. The framework stops the request and serializes its detail value.

The more interesting policy sits at the AI boundary. fallback_brief() runs first. If AI enhancement is disabled, that brief is the final result. If enhancement is enabled, the code distinguishes invalid model content from operational failure:

A ValueError means the model was reachable but its response did not satisfy strict JSON parsing. A network exception takes the degraded path. Both preserve useful output, but their status metadata tells operators two different stories.

There is a second deadline around the entire enrichment operation:

Python's asyncio.wait_for() documentation says a timeout cancels the awaited operation and raises TimeoutError. It also warns that cancellation itself can make elapsed time exceed the numeric timeout, so this is a response budget, not a benchmark guarantee.

Two clocks, two jobs

It helps to separate the timeout inside the model client from the timeout around the use case. In ollama_brief(), lines 2421–2432, HTTPX receives AI_TIMEOUT_SECONDS for the POST, checks the HTTP status, reads the JSON envelope, and then sends the model's text to a stricter object extractor. That timeout governs network work. The outer asyncio.wait_for() governs how long ticker search is willing to wait for the whole enrichment coroutine.

HTTPX documents four timeout categories: connect, read, write, and pool. A scalar timeout configures a general limit; a production service can split those categories when, for example, connecting should fail quickly but model generation may legitimately take longer to produce response data. The outer budget remains useful even then because it represents a product decision rather than a transport detail: after this point, rebuild the deterministic brief from the quote already in hand.

Status is part of the contract

If object extraction raises ValueError, the service knows enough to say the model endpoint was reachable but its content was unusable. A ReadTimeout says response data did not arrive within the configured read allowance. The payload survives both failures; the metadata preserves the diagnostic difference.

Test outcomes, not live dependencies

FastAPI's TestClient testing guide shows how to exercise an application without opening a real HTTP socket. For the internal async functions, pytest's monkeypatch fixture guide explains how to replace the model call for one test and restore it afterward. That lets us produce each failure on demand—no stopped containers, invalid DNS, or sleeping test suite required.

Now add the two timeout cases:

The httpx.Request in the first test is only attached to the synthetic exception; it sends nothing. HTTPX documents ReadTimeout as a subtype of TimeoutException, specifically for timing out while receiving response data. The second test injects TimeoutError at the function boundary. It verifies the application's recovery contract immediately rather than making the suite wait for the configured three-to-four-second budget.

A seam test, not a stopwatch test

The request-budget case proves what research_brief_for_request() does when it receives the exception promised by asyncio.wait_for(). It does not attempt to prove Python's cancellation implementation or measure operating-system scheduling. The standard library owns those mechanics; this application owns the resulting brief, metadata, and cache entry.

The mix of one HTTP-level test and three function-level tests is intentional too. TestClient is the right level for confirming that HTTPException becomes the expected JSON response and status code. Direct calls are the right level for distinguishing malformed model content from transport failure without mocking the unrelated market-data and search branches used by /api/analyze. A larger endpoint test could patch every dependency and assert the complete response, but it would obscure the small failure contract we care about here.

This split makes failures easier to read. If the 400 case breaks, inspect routing, validation, or exception translation. If a fallback case breaks, inspect the model boundary. If the cache assertion breaks, inspect timeout recovery. Each test names one policy and introduces only the minimum synthetic failure needed to reach it.

What these four tests buy you

Input contractMalformed ticker → HTTP 400 with the domain error intact.
Content contractInvalid model JSON → deterministic brief with reachable-status context.
Transport contractHTTPX read timeout → deterministic brief and degraded AI status.
Budget contractRequest timeout → deterministic brief, degraded status, and cache write.

The first test protects error taxonomy. A malformed ticker is the caller's problem, so it must not be blurred into the endpoint's 404 path for unavailable market data. The next two protect graceful degradation: bad AI output and a network timeout both preserve the deterministic brief, while the dependency metadata remains specific enough to diagnose the difference. The final test protects the latency escape hatch and the cache write that follows it.

Notice what the tests do not assert. They do not freeze generated timestamps, reproduce a model's prose, depend on a particular stock price, or claim a performance number. Those would make the suite brittle or misleading. The stable contract is smaller: response class, fallback source, dependency state, diagnostic category, and cache outcome.

There is also a useful hardening lesson in the production excerpt. The broad except Exception keeps this public demo available, but it can also convert an unexpected programming defect into a degraded dependency message. In a service with stricter observability requirements, I would narrow that catch to expected HTTPX, parsing, and protocol exceptions, then let unknown defects surface to error monitoring. The deterministic tests still help: they define the behavior that must survive that refactor.

Graceful degradation becomes trustworthy only when it is repeatable. Build the fallback before the optional call, make status metadata part of the response contract, bound the wait, isolate shared state, and force each failure in tests. Then “the AI is optional” is no longer an optimistic architecture diagram. It is an executable guarantee.
